===== Репликация
автоматическое копирование изменений БД с одного узла на другие
Виды:
Физическая (streaming, WAL): побайтовая реплика всего кластера. Реплики «только чтение». Просто и быстро.
Логическая: реплицируются операции над строками для выбранных таблиц/схем. Гибко, подходит для частичных копий и
апгрейдов между версиями.

репликация почти всегда оставляет одного писателя → не увеличивает пропускную способность записей.

===== Партиционирование
разбиение одной таблицы на части (партиции) по ключу (дата, tenant_id, hash) в пределах одного сервера/кластера.
быстрее запросы за счёт отсечения лишних партиций (pruning), дешёвая чистка старых данных (DROP PARTITION), проще
обслуживание (VACUUM/индексы по частям).
Виды: RANGE, LIST, HASH (возможна субпартиция).
локальная техника — не про «много серверов». Глобальных уникальных ключей нет без включения ключа партиционирования


===== Шардирование
горизонтальное распределение строк одной логической таблицы по нескольким серверам (шардам) по ключу (hash/range).
масштабировать объём и записи (несколько узлов пишут параллельно), убрать горячие точки.

разделение на несколько физических серверов

1) Репликация «один писатель → много читателей»

Задача: поднять отказоустойчивость и масштабировать чтения.
Как работает: есть primary (все записи) и standby (только чтение) через физическую streaming-репликацию (WAL).
Когда: чтений много, записи умеренные; нужен HA.

Механизмы:
Физическая репликация (WAL streaming), sync/async, каскадная.
Оркестрация HA: Patroni + etcd/Consul, Stolon, repmgr.
R/W-роутинг: HAProxy/pgpool-II, или в коде.

Плюсы/минусы: просто, надёжно; не масштабирует записи.
Тактика роста: 1→N реплик; при жёстком RPO≈0 — одна синхронная реплика.



2) Логическая репликация (частичное разнесение)

Задача: разнести часть таблиц на другой сервер/кластер, онлайн-миграции версий.
Как работает: публикуем таблицы (publication) и подписываемся (subscription) — перекачиваются операции INSERT/UPDATE/DELETE.
Когда: вынести отчётные/реад-хеви таблицы, апгрейд без простоя, построить «витрину».
Плюсы/минусы: гибко, межверсионно; DDL не реплицируется автоматически, думать о ключах/конфликтах.


3) Федерация (объединение чужих БД в один слой запросов)

Задача: читать данные с других серверов как будто это ваши таблицы.
Как работает: postgres_fdw создаёт внешние таблицы, планировщик часть запроса «толкает» на удалённый сервер.
Когда: админки, редкие кросс-сервисные отчёты; интеграция микросервисных БД.
Плюсы/минусы: быстро «склеить» чтение; не для тяжёлых OLTP-JOIN по сети.



4) Шардирование (горизонтальное деление строк по серверам)

Задача: масштабировать объём и записи, когда один сервер упёрся.
Как работает: делим таблицы на шарды по ключу (hash/range); запросы маршрутизируются на нужный сервер; кросс-шардовые операции — дороже.

Стратегии распределения:
Hash-шард: равномерные записи, хуже range-сканы.
Range-шард: удобно гео/время/tenant-диапазоны, риск «горячего» шарда.
Geo-шард: «данные ближе к пользователю» (по региону).

Координатор/роутер:
Citus (экстеншен): координатор + воркеры, create_distributed_table('orders','tenant_id','hash'), reference-таблицы для справочников, co-location для JOIN.
Ручной роутинг + FDW: каталог «ключ → шард», отправка из кода; агрегации через сервис-агрегатор/FDW.

ID и уникальности:
UUIDv7/ULID или «пачки»/шаги для sequences (например, INCREMENT BY N, разные START для каждого шарда).
Глобальных FK «из коробки» нет → валидируйте на приложении/асинхронно.

Транзакции:
По-возможности — внутри одного шарда. Межшардовые — сага/идемпотентность; 2PC — осторожно.
У Citus есть распределённые транзакции с координацией.

Плюсы/минусы: масштаб записей/объёма; сложнее JOIN/миграции/ребаланс.



5) Партиционирование как «ступенька» к распределению

Задача: ускорить большие таблицы и подготовиться к разнесению.
Как работает: одна логическая таблица → много партиций (RANGE/LIST/HASH) на одном сервере, но дальше партиции/«бакеты» удобно вывозить на шарды.

Тактики:
RANGE по времени для ретеншна (DROP PARTITION) и холодного архива (на другой сервер через логическую репликацию).
HASH — сгладить «горячие» ключи; затем бакеты разложить по шардам.



6) Мульти-мастер / двунаправленная логическая репликация

Задача: актив-актив запись в нескольких ЦОД/регионах.
Как работает: двусторонние публикации/подписки, разрешение конфликтов.

Когда: редкие случаи (офлайн-офисы, гео-запись обязательна).
Механизмы: BDR/pglogical (симметричная настройка), дисциплина ключей и правил конфликтов.
Минусы: сложность DDL/конфликты/тесты — использовать только при жёсткой потребности.



7) DR/Geo-репликация (между дата-центрами)

Задача: катастрофоустойчивость.
Как работает: асинхронная физическая реплика в другой DC/регион; иногда с задержкой применения WAL, чтобы защититься от случайного удаления.

Тактики: отдельное S3/объектное хранилище для WAL, регулярные «тренировки» восстановления.



8) Вытеснение тяжёлых чтений во внешние системы (CQRS/CDC)

Задача: разгрузить PostgreSQL, когда и шард дорого для аналитики/поиска.
Как работает: логическое декодирование → Debezium/Kafka → витрины: Redis (кэш), OpenSearch/Elastic (поиск), ClickHouse/Druid (OLAP).
Роль: не «делит» Postgres сам по себе, но позволяет держать больше серверов вокруг (каждый со своей специализацией) и разгружать основной кластер.

Партиции и Шардинг:

Партиционирование больших/растущих таблиц: Вы берёте огромную таблицу (например, с данными логов, событий или транзакций), которая постоянно пополняется новыми записями, и разделяете её на более мелкие, управляемые части, называемые партициями.
(Обычно RANGE по дате): В качестве ключа, по которому происходит разделение, выбирается столбец с типом данных "дата" (DATE или TIMESTAMP). Это наиболее естественный способ для данных, которые накапливаются со временем. Партиции создаются для определённых диапазонов дат — например, одна партиция на каждый месяц или год.
Быстрое удаление старых данных: Одно из главных преимуществ такого подхода. Вместо того чтобы выполнять медленную операцию DELETE FROM ... WHERE date < '...' по миллиардам строк, что приводит к значительной нагрузке на базу данных и блокировкам, вы просто удаляете (или отсоединяете) целую партицию. Операция DROP TABLE или ALTER TABLE DETACH PARTITION выполняется практически мгновенно, так как это просто удаление файла или отсоединение логического указателя.
Подготовка к шардингу: Партиционирование внутри одной базы данных является логическим первым шагом к шардингу. Когда таблица становится настолько большой, что даже партиционирования на одном сервере становится недостаточно, вы можете легко перенести одну или несколько партиций (каждая из которых, по сути, является обычной таблицей) на другой сервер. Это позволяет распределить нагрузку на несколько машин без необходимости переписывать всю архитектуру данных.

1) Пул подключений перед БД (PgBouncer)

Зачем: выдерживать тысячи краткоживущих коннектов; must-have для дальнейших этапов.
Когда: много сервисов/воркеров, REST/gRPC лавина коннектов.

Да. В PostgreSQL модель «процесс на подключение»: на каждый клиентский коннект форкается backend-процесс ОС.
Это не тред внутри одного процесса, а именно отдельный процесс.
JDBC “сам по себе” (через DriverManager.getConnection() без пула) — будет открывать физический коннект каждый раз → неоптимально.
Нужен пул.

Есть ли «свой пул» в Hibernate/JPA?

Hibernate/JPA не содержит полноценного производственного пула по умолчанию.
Он ожидает DataSource с пулом: HikariCP (де-факто стандарт), Apache DBCP, c3p0, пул сервера приложений
(WildFly/IronJacamar, Quarkus/Agroal и т.п.).
Если вы «ничего не настраивали», в некоторых сборках Hibernate может использовать простой провайдер коннектов 
(каждый раз открывает/закрывает) — это не для продакшена.
В Spring Boot по умолчанию как раз подставляется HikariCP — это правильно.
Важно: «пул потоков» ≠ «пул подключений». Потоки обрабатывают запросы, подключения к БД — отдельный ограниченный ресурс,
их тоже надо пулить.

Нужны ли оба: Hikari и PgBouncer?

Короткий ответ: часто — да, оба, но с правильными настройками. Подробно:
- Когда хватит только Hikari (без PgBouncer)
- У вас 1–2 приложения и суммарно несколько десятков соединений.
- DB и апп рядом, нет «лавины» коротких коннектов (lambda/serverless).
- Нужны фичи «сессионного» состояния: server-side prepared statements, LISTEN/NOTIFY, долгоживущие курсоры, TEMP-таблицы между транзакциями. (Это плохо дружит с transaction-режимом PgBouncer.)

Когда лучше только PgBouncer (а в приложении — минимальный/нулевой пул)
- Среда serverless/функции: куча очень коротких коннектов → PgBouncer спасает мультиплексированием.
- Много разрозненных клиентов/языков без хороших пулов.
- Хотите централизовать лимит соединений и «прикрыть» БД единым входом.
- (Всё равно разумно держать маленький пул в клиенте, чтобы не долбить PgBouncer коннект/дисконнектом на каждый запрос.)

Когда использовать оба (типовой прод для микросервисов)
- Микросервисы: 10+ сервисов × по 10–50 коннектов каждый = легко превысите max_connections у БД.
- Ставим PgBouncer перед БД (обычно pool_mode=transaction), а в каждом сервисе — Hikari с маленьким пулом (например, 10–20).
- Итог: Hikari агрегирует запросы внутри сервиса, PgBouncer мультиплексирует сотни клиентских коннектов в несколько десятков реальных коннектов к Postgres.

Что такое пул ПОТОКОВ vs пул КОННЕКТОВ

Пул потоков (thread pool) — это про CPU в приложении.
Набор заранее созданных рабочих потоков, которые берут задачи из очереди: обработка HTTP-запросов, сериализация JSON, вызовы сервисов и т.д. Примеры: Tomcat maxThreads, Jetty, Netty event loop + worker pool, ExecutorService в Java.

Пул подключений (connection pool) — это про сеансы к БД.
Небольшой набор заранее открытых соединений к Postgres, которые по запросу «выдаются» потокам и потом возвращаются в пул. Примеры: HikariCP (в приложении), PgBouncer (в отдельном процессе между приложением и PG).

> Итог: пул потоков управляет потоками приложения; пул подключений управляет сеансами к БД. 
> Это разные уровни, но они работают вместе.

Так Hikari — это что? А PgBouncer — что?
HikariCP — пул подключений JDBC внутри вашего приложения. Он держит несколько реальных TCP-коннектов к БД (или к PgBouncer), а вашему коду выдаёт «логические» Connection. Когда вы вызываете close(), соединение не закрывается, а возвращается в пул.
Hikari не «пул потоков». У него есть 1–2 сервисных треда для housekeeping, но назначение — именно пул БД-коннектов.
PgBouncer — тоже пул подключений, но снаружи приложения, как лёгкий прокси перед Postgres. Он умеет мультиплексировать тысячи клиентских коннектов в десятки серверных, особенно в режиме pool_mode=transaction.

PgBouncer — это лёгкий прокси-пул подключений между приложением и PostgreSQL.
Postgres дорог по схеме «1 клиент = 1 серверный процесс». Тысячи микросервисов × по 20–50 коннектов каждый — и БД
захлебнулась. PgBouncer держит небольшой пул настоящих серверных коннектов и мультиплексирует через них тысячи клиентских.

Как работает (идея)
Клиенты коннектятся к PgBouncer, а он — к Postgres.
Когда приходит запрос, PgBouncer выдаёт клиенту один из уже открытых серверных коннектов, выполняет запрос и возвращает
серверный коннект в пул.
Это резко снижает число реальных коннектов к Postgres и их «пересоздание».

Режимы пуллинга
- session — серверный коннект закрепляется за клиентом на всю сессию.
- transaction (чаще всего в проде) — закрепление на время транзакции.
- statement — на один запрос. Используют редко.

Где ставить
В проде обычно отдельный сервис/VM рядом с БД (дешевле сеть).
Можно «сайдкаром» рядом с приложением — уменьшит сетевые RTT.

HikariCP - на клиенте
PgBouncer - на сервере


Делаем:

Ставим PgBouncer, режим transaction (если нет долгих session-state фич).
Аппы подключаются к PgBouncer, PgBouncer — к PostgreSQL.
Отключаем server-side prepared statements (или настраиваем reset).
Риски: курсоры/временные таблицы/Advisory locks в transaction-режиме — мимо. Тогда session.
Идём дальше, если: чтений много → хотим масштабировать чтения репликами / повышать доступность.

2) Одна физическая read-реплика (asynchronous streaming)

Зачем: разгрузить чтения, быстрые бэкапы, подготовка к HA.
Когда: чтения доминируют или бэкапы мешают продакшену.

Делаем:

На primary:

wal_level=replica
max_wal_senders=10
hot_standby=on


Инициализация standby:

pg_basebackup -h <primary> -D /var/lib/pgsql/standby -R -P


Запускаем standby; настраиваем pg_hba.conf.

Переносим бэкапы на реплику; начинаем мягко переводить отчёты/чтения.

Риски: лаг → «несвежие» чтения; последовательности на реплике не безопасны для записи.

Идём дальше, если: нужен SLA по RPO≈0/RTO низкий и/или уже хотим авто-failover.

3) HA с авто-failover (один writer): Patroni + etcd/Consul (+ HAProxy)

Зачем: отказоустойчивость без ручного вмешательства.
Когда: простой standby уже есть, нужен автомат.

Делаем:

Кластер из 3+ нод кворума (etcd/Consul).

На PG-нодах — Patroni, который управляет ролями.

HAProxy/Keepalived даёт стабильные эндпоинты: writer:5432, reader:5432.

Клиенты ходят через прокси; failover прозрачен.

Риски: split-brain при неправильном кворуме/сетях; нужна дисциплина DCS.

Идём дальше, если: чтений всё ещё не хватает → добавляем реплики, вводим синхронность для RPO≈0.

4) Масштабирование чтений: несколько read-реплик + read/write split

Зачем: линейно наращивать пропускную способность чтений.
Когда: отчёты, API-GET, аналитики много.

Делаем:

2–N standby. Одна из них может быть синхронной (см. ниже).

В HAProxy/pgpool-II — read/write routing (по user/DB/SQL-признаку).

В коде — явный роутинг (BFF-паттерн), если прокси не отличает.

Опционально: synchronous_commit=on, synchronous_standby_names='FIRST 1 (nodeA,nodeB)' → RPO≈0 ценой латентности записи.

Риски: не все запросы годятся на реплику (требуется read-your-writes); следить за лагом.

Идём дальше, если: нужно онлайн-обновление/миграции и/или вынесение части таблиц.

5) Логическая репликация для: (а) отчётного кластера, (б) онлайн-миграций

Зачем: частично разнести нагрузку/таблицы, делать апгрейды без простоя.
Когда: отчёты мешают OLTP, нужно перелить схему/версию «на лету».

Делаем:

Включаем wal_level=logical.

На источнике:

CREATE PUBLICATION app_pub FOR TABLE public.orders, public.users;


На приёмнике:

CREATE SUBSCRIPTION app_sub
CONNECTION 'host=src dbname=app user=replicator password=***'
PUBLICATION app_pub WITH (copy_data = true);


Для cutover: заморозить запись на минуту → догнать лаг → переключить DNS/прокси.

Риски: DDL не реплицируется автоматически → миграции в обоих концах; осторожно с unique/триггерами.

Идём дальше, если: аналитика/поиск всё равно тяжёлые → выносим чтения во внешние движки.

6) Снятие тяжёлых чтений через CDC/CQRS (Redis/Elastic/ClickHouse)

Зачем: убрать «дорогие» запросы из PG, высвободить CPU/IO.
Когда: полнотекст, фасеты, OLAP-агрегаты, TTL-кэш нужен быстро.

Делаем:

Логическое декодирование → Debezium → Kafka/Redpanda.

Консьюмеры собирают materialized views: Redis (кэш), Elastic/OpenSearch (поиск), ClickHouse/Druid (аналитика).

В приложении — CQRS: записи → PG, чтения → витрины.

Риски: идемпотентность, порядок, задержка обновления витрин.

Идём дальше, если: упёрлись в записи/объём одного writer.

7) Между ЦОД/регионами: DR-реплика (asynchronous)

Зачем: катастрофоустойчивость (другой DC/регион), RPO>0 приемлем.
Когда: требования бизнеса по DR.

Делаем:

Доп. асинхронная реплика в другой DC (часто с задержкой реплея WAL, чтобы пережить «удалил всё»).

Отдельный объект-хранилище для WAL-архива (S3-совместимое).

Риски: медленная сеть, ежедневный тест восстановления обязателен.

Идём дальше, если: записи не помещаются на один узел → переходим к шардингу.

8) Шардирование: Citus или «ручной» шардинг + FDW/роутер

Зачем: горизонтально масштабировать объём и записи.
Когда: один writer — узкое место, таблицы ≫ сотен млн/миллиардов строк.

Вариант A: Citus

Как работает: координатор распределяет запросы по воркерам; таблицы делятся по ключу (hash/range), reference-таблицы копируются.

Делаем:

-- На Citus:
SELECT create_distributed_table('orders','tenant_id','hash');
SELECT create_reference_table('products');

-- Перенос: логическая репликация/копия; поэтапно переводим трафик.


Плюсы: прозрачнее для SQL, co-location для join/agg, rebalancing инструментами Citus.
Минусы: зависимость от расширения, свои ограничения планировщика.

Вариант B: Ручной шардинг

Как работает: несколько обычных кластеров; роутинг в коде/прокси; агрегирующие запросы через postgres_fdw/сервис-агрегатор.

Делаем:

Выбор ключа (часто tenant_id). Диапазоны/консистентный hash.

Каталог шардов (метаданные, куда писать/читать).

Сервис-роутер/BFF, который отправляет запросы на нужный шард.

Для cross-shard отчётов — асинхронные джобы/витрины.

Плюсы: полный контроль, нативный Postgres.
Минусы: больше логики в приложении, тяжелее cross-shard операции.

Общие риски шардинга: глобальная уникальность PK/FK, транзакции между шардами, ребаланс шардов при росте.

Где встраивать партиционирование

Рано (этап 0–2): для растущих таблиц (RANGE по дате или HASH для горячих ключей).

Поможет скоростному ретеншну (DROP/DETACH PARTITION) и подготовит к шардированию (один шард = набор партиций).

Мини-шпаргалка по переходам

Пул коннектов → выдерживаем нагрузку сессий.

1 реплика → разгрузка чтений/бэкапов.

HA (Patroni) → авто-failover, SLA.

N реплик + роутинг → масштаб чтений.

Логическая репликация → отчётный кластер / онлайн-апгрейды.

CDC/CQRS → убираем поиски/OLAP из PG.

DR в другом DC → катастрофоустойчивость.

Шардирование → масштаб записей и объёма.

Примеры минимальных команд/настроек (суммарно)

Создать standby:

# на реплике
pg_basebackup -h primary -U repl -D /pgdata -R -P


Синхронная запись (кворум 1):

synchronous_commit = on
synchronous_standby_names = 'FIRST 1 (standby_a, standby_b)'


Публикация/подписка (логическая):

CREATE PUBLICATION pub_app FOR TABLE public.orders, public.users;
CREATE SUBSCRIPTION sub_app
CONNECTION 'host=primary dbname=app user=replicator password=***'
PUBLICATION pub_app WITH (copy_data=true);


FDW:

CREATE EXTENSION postgres_fdw;
CREATE SERVER shard1 FOREIGN DATA WRAPPER postgres_fdw OPTIONS (host '10.0.1.10', dbname 'app');
CREATE USER MAPPING FOR app SERVER shard1 OPTIONS (user 'app', password '***');
CREATE FOREIGN TABLE orders_s1 (...) SERVER shard1 OPTIONS (schema_name 'public', table_name 'orders');


Партиционирование по месяцу:

CREATE TABLE events(..., ts timestamptz NOT NULL) PARTITION BY RANGE (ts);
CREATE TABLE events_2025_10 PARTITION OF events FOR VALUES FROM ('2025-10-01') TO ('2025-11-01');
CREATE TABLE events_default PARTITION OF events DEFAULT;

Что сказать бизнесу на каждом шаге

Этапы 1–4: растим чтения и доступность; RTO минуты, RPO вплоть до 0 (при синхроне).

Этап 5–6: нулевой простой на апгрейдах, быстрый поиск/аналитика без вреда OLTP.

Этап 7: переживаем потерю DC (с допускаемым RPO).

Этап 8: масштабируем записи/объём горизонтально, цена — сложнее транзакции и эксплуатация.
