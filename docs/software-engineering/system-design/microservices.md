## Выделение микросервисов

Domain Driven Design (DDD). Подход доменно ориентированного проектирования

Обязывает создавать абстракции в которые входит бизнес-логика. (Связующее звено между бизнесом и ПО, для ускорения разработки в незнакомой предметной области)

Домен -- предметная область для которой ведется разработка. Так же есть Поддомены.
Бизнес-процесс -- сквозной сценарий/поток действий («Оформить заказ», «Возврат денег»). Он может проходить через несколько команд/областей.
Бизнес-возможность (capability) -- устойчивая «функция бизнеса» («Управление заказами», «Платежи», «Каталог»). Это то, «что умеет организация».
Ограниченный контекст (bounded context) -- граница единой модели и инвариантов (своя терминология, правила, транзакции). Здесь данные и правила согласованы.
Микросервис -- техническая упаковка одного (иногда части) bounded context’а с его API и хранилищем.


- Ubiquitous Language (Единый язык) -- все термины, сущности, бизнес процессы, методы и тд в коде называются и означают то же самое что и в предметной области бизнеса.
- Subdomains (Подобласти/поддомены) -- отделы в компании = разные поддомены, чтобы не было коллизий, тк одни и те же термины и сущности могут отличаться в разных отделах.
- Контексты -- выделение бизнес процессов внутри поддоменов. Должна быть четкая граница для каждого контекста для разграничения зон ответственности и для распараллеливания работы.

> Каждый микросервис должен совпадать с одним устойчивым bounded context’ом.
Но не каждый bounded context обязан сразу становиться микросервисом

Как связать процессы и сервисы


как коммуницируют между собой микросервисы Синхрон: REST/gRPC Асинхрон/события: Kafka/RabbitMQ/NATS

Шаблоны обращения:
    API Gateway (единая точка входа: auth, rate-limit, routing, CORS).
    Service Discovery (Eureka/Consul/K8s DNS).
    API Composition / Aggregator (слить данные из нескольких сервисов для фронта).
    Backends for Frontends (BFF) -- узко под конкретный UI/мобильный.

Данные и согласованность
    Транзакции в распределённом мире: избегай 2PC.
    Согласованность: eventual через SAGA и Outbox.
        SAGA:
            Choreography -- цепочка событий (просто, но может быть «event spaghetti»).
            Orchestration -- отдельный оркестратор (понятнее потоки).
    Transactional Outbox + CDC (Debezium): записываем событие рядом с бизнес-транзакцией → надёжная публикация в брокер.
    Идемпотентность: ключи/версии, чтобы повтор не ломал состояние.
    Схемы и эволюция: schema registry (Avro/Protobuf), backward-compatible изменения.

Надёжность и отказоустойчивость (Resilience)
    Circuit Breaker, Retry (с джиттером), Timeout, Bulkhead, Rate Limiting, Backpressure.
    Dead Letter Queue для неуспешных сообщений.
    Idempotency keys на входах с возможным повтором.
    Кэш (Redis) для горячих чтений/тяжёлых агрегаций.

Масштабирование
    Статлесс сервисы → горизонтально (HPA).
    Read-реплики, CQRS-чтения для тяжёлых запросов.
    Шардирование/партиционирование (в БД и в Kafka).
    Тяжёлые задачи в async-воркерах (очереди, отложенные задачи).

Набор ключевых паттернов (минимум must-know)
    Gateway / BFF / Discovery
    SAGA (choreography/orchestration)
    Outbox + CDC
    CQRS (раздельные модели чтения/записи)
    Event Sourcing (источник истины -- поток событий; реже, сложнее)
    Circuit Breaker / Retry / Bulkhead
    Strangler Fig (миграция с монолита)
    Blue-Green / Canary releases
    Feature Flags

Наблюдаемость (observability)
Три столпа: логи, метрики, трейсы.
    OpenTelemetry SDK + Collector →
    traces в Jaeger/Tempo, metrics в Prometheus → Grafana, logs в Loki/ELK.
    Корреляция: traceId сквозь gateway → сервисы → БД/брокер.
    Технические метрики: rps, p95/p99, error rate, saturations; бизнес-метрики: конверсия, SLA доменных операций.

Безопасность
    AuthN/AuthZ: OAuth2/OIDC (Keycloak/Auth0), JWT, opaque tokens; RBAC/ABAC.
    mTLS внутри контура (особенно с сервис-мэшем).
    Секреты: Vault/K8s Secrets/SOPS.
    Политики: rate-limits, WAF, входная и выходная валидация схем.

Доставка и платформенная часть
    Контейнеризация: Docker/Buildpacks.
    Оркестрация: Kubernetes (+ Helm/Kustomize; HPA, PDB, Pod requests/limits).
    Service Mesh (Istio/Linkerd) -- mTLS, retries, канареечные маршруты без изменения кода.
    CI/CD: GitHub Actions/GitLab CI; GitOps (Argo CD/Flux).
    Среда разработчика: Docker Compose (локально), kind/k3d + Tilt/Skaffold для live-reload.
    Конфигурации: 12-factor, Spring Cloud Config/Consul, переменные окружения.

Тестирование и качество
    Пирамида тестов: unit → slice/integration (Testcontainers) → e2e.
    Contract Testing (CDC): Pact/SPRING Cloud Contract между потребителем и провайдером.
    Chaos Engineering: fault injection для проверки устойчивости.
    Migration tests: Flyway/Liquibase миграции прогоняются в CI на чистой БД.
