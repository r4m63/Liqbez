# CLAUDE.md — как писать заметки в liqbez

## Назначение

Этот репозиторий — личные технические заметки на русском: deep-dive по технологиям, шпаргалки, конспекты. Не код, не продакшн. Цель этого файла — задать стиль, в котором Claude дописывает и редактирует markdown-документы здесь.

Каноны стиля:
- `postgres/README.md` — концептуальный deep-dive
- `postgres/scale-postgres.md` — практичная шпаргалка

> Если этот файл противоречит свежим документам в репозитории — побеждают документы. Обновляй guide, а не подгоняй заметки под устаревшее правило.

## Аудитория и тон

Читатель — сам автор спустя месяцы, или коллега с похожим бэкграундом. Пишем как объясняем за кофе человеку, который уже знает основы — а не как Wikipedia для случайного посетителя.

- База — безличная форма: «сначала измеряешь», «не масштабируй, пока не понял узкое место».
- «Ты» допустимо в советах и предупреждениях. «Вы» и «мы» — никогда.
- Короткие рублёные предложения. Если предложение длиннее ~20 слов — режь.
- Допустимы маркеры неопределённости и нужны: «обычно», «часто», «почти всегда», «грубо говоря», «в проде чаще». Реальность вероятностная — не пиши абсолютами там, где их нет.

## Язык: русский + английские термины

Английские технические термины — как есть, без транслита, без курсива, без кавычек.

Не переводим: WAL, primary, standby, snapshot, backend, vacuum, autovacuum, replication, failover, sharding, partitioning, query planner, index, lock, checkpoint, deadlock, bottleneck, throughput, latency, scale-out, scale-up, commit, rollback, OLTP, OLAP, MVCC, ACID.

Транслитерация только для слов, давно ушедших в русский: «кэш», «бэкенд» (в неформальном контексте), «бэкап». В техническом тексте лучше английский.

Команды, флаги, имена утилит, пути — в backtick, всегда по-английски: `pg_stat_statements`, `PGDATA`, `VACUUM FULL`.

## Структура документа

- H1 — один на файл, название топика: `# MVCC`, `# Архитектура Postgres`.
- H2 — крупные разделы.
- H3 — подразделы внутри H2.
- Глубже H3 не уходим — переделай в плоский список или вынеси в отдельный файл.

В начале документа (после H1) — короткое вступление 2–4 строки или блок «Главная идея:». Без TOC, кроме случаев, когда файл — индекс папки.

## Заголовки и нумерация

- Нумеруем заголовки (`## 1.`, `### 1.1.`) только в пошаговых документах и шпаргалках, где порядок важен (scale-postgres.md стиль).
- В концептуальных deep-dive не нумеруем (README.md стиль).
- Не дублируем заголовок в первой строке текста под ним.

## Разделители

- Горизонтальный разделитель — всегда линия из 100 дефисов, не короткий `---`. Markdown рендерит и то, и другое одинаково, но в сыром тексте длинная линия читается как реальная граница раздела:

```
----------------------------------------------------------------------------------------------------
```

- Используется между крупными разделами H2, иногда внутри одного H2 между смысловыми блоками, когда подзаголовка не хочется.
- Голый `---` не пишем — если уже есть, заменяй на длинную форму.

## Определения и метки-секции

Шаблон определения:

```
**Термин** — это X.
- развёртка
- развёртка
```

Em-dash (` — `), одно предложение в определении. Дальше — буллетами.

Метки-секции — мини-заголовки внутри блока, без markdown-heading:

`Когда подходит:`, `Плюсы:`, `Минусы:`, `Ограничения:`, `Зачем:`, `Что делает:`, `Идея простая:`, `Если не делать X:`, `Грабли:`.

После метки — двоеточие, дальше с новой строки буллеты.

## Списки и таблицы

- Буллеты только через `-`. Не `*`, не `+`.
- Шаблон строки: `- термин — объяснение`.
- Вложенность максимум на 2 уровня. Глубже — переделай в подзаголовок.
- Не нумеруй буллеты вручную (`1.`, `2.`) внутри `-`-списка. Используй `1.`-список, если порядок реально важен.
- `<br/>` внутри буллета — когда внутри одного пункта 2–4 строки и вложенный список избыточен.

Таблицы — только для сравнений по фиксированному набору колонок (режимы репликации, симптом → действие, опция → эффект). Если в ячейке больше ~10 слов — это не таблица, это буллеты.

## Код, пути, идентификаторы

- Backtick для идентификаторов, путей, команд inline: `pg_stat_statements`, `$PGDATA/base`.
- Fenced блоки с языковыми тегами всегда: ` ```sql `, ` ```bash `, ` ```txt ` для ASCII-схем.
- Структуры директорий — ASCII-деревом в ` ```txt ` (см. PGDATA в `postgres/README.md`).

## Callouts

- `> [!NOTE]` — сайдбар-факт, нюанс, который иначе ломал бы поток основного текста.
- `>` без типа — финальное правило/афоризм в конце документа («Главное правило: …»).
- Других типов (`[!WARNING]`, `[!TIP]`) не используем — держим набор минимальным.

## Длина

- Предложение — короткое. Длиннее ~20 слов — режь.
- Абзац — 1–4 предложения. Дальше — буллеты или подзаголовок.
- Буллет — короткая мысль, 1–2 предложения. Длинный буллет — выноси в подраздел.
- Документ в целом — пока пишется естественно. Не разбухай ради полноты, не режь ради краткости.

## Перенос строк

- Максимальная длина физической строки — 100 символов (по ширине разделителя). Простой текст и буллеты переноси на следующую строку, когда упираешься в этот лимит.
- Перенос делаем по смысловой границе (после запятой, точки, тире), а не посреди слова.
- При переносе буллета продолжение пишем с отступом, чтобы визуально читалось как один пункт:

```
- **Длинный термин** — первая часть мысли, которая логично заканчивается перед запятой,
  и продолжение со второго уровня отступа (два пробела).
```

- Исключения, которые НЕ переносим:
  - Таблицы — ячейки и строки идут как есть, даже если строка длиннее 100.
  - Fenced code blocks (` ```... ``` `) — содержимое не трогаем.
  - URL и длинные пути — целиком в одну строку.
  - ASCII-схемы / деревья директорий — не ломаем визуал.
  - Заголовки — не переносим, если получилось длинно — переформулируй короче.

## Начало и конец документа

Начало:
- H1 с названием топика.
- 2–4 строки вступления или явный блок «Главная идея:» с короткой формулировкой.

Конец — один из трёх вариантов:
- Просто последний H2, без саммари.
- Шпаргалочный блок «Если коротко:» с буллетами `Симптом → действие` или `Сценарий → решение`.
- Финальная блок-цитата `> Главное правило: …`.

И больше ничего. Никаких «итак, мы рассмотрели».

## Антипаттерны (запрещено)

- Саммари в начале раздела: «В этом разделе мы рассмотрим…».
- Саммари в конце документа: «Итак, мы изучили…».
- Закрывающие фразы: «Надеюсь, это поможет», «Если есть вопросы…».
- Перевод устоявшихся английских терминов: WAL остаётся WAL, не «журнал упреждающей записи».
- Эмодзи. Исключение — внутри `> [!NOTE]`, где иконка рендерится автоматически.
- `**жирный**` для произвольного эмфазиса в тексте. Только для имён терминов в шаблоне определения и для подписей-меток (`**Плюсы:**` в контекстах, где уже есть жирные заголовки рядом).
- Курсив `*текст*` для интонации.
- Повтор заголовка в первой строке под ним.
- TOC в обычных документах (только в индексных README).
- Абсолюты («всегда», «никогда») там, где реальность вероятностная.
- Академические связки: «таким образом», «следовательно», «как видно из вышесказанного», «давайте рассмотрим», «стоит отметить».
- Буллеты через `*` или `+`.
- Внешние ссылки без необходимости. Это личные заметки, не литобзор. Ссылка уместна, если ведёт к источнику, на который опираешься.

## README/index vs обычный документ

- `README.md` в папке топика — только если файлов в папке больше пяти и нужна навигация. Тогда вверху — bullet-список ссылок на остальные документы (см. `postgres/README.md`).
- Иначе документы лежат плоско, без индекса.
- README сам может быть полноценным deep-dive после блока ссылок — это норма.

## Чек-лист перед сохранением

- Английские термины не переведены.
- Нет эмодзи (вне `[!NOTE]`).
- Нет закрывающего саммари.
- Нет «давайте/рассмотрим/следует отметить».
- Определения в шаблоне `**Термин** — это X.` с em-dash.
- Буллеты через `-`, не `*`.
- Заголовок не дублируется в первой строке под ним.
- Если документ — шпаргалка, в конце есть «Если коротко:» или `> Главное правило: …`.
- Звучит как объяснение коллеге, а не как Wikipedia. Если сомневаешься — перечитай вслух.
