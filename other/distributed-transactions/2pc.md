# 2PC / XA


**2PC** (`Two-Phase Commit`) — это протокол, который пытается атомарно завершить одну транзакцию
сразу на нескольких участниках.

- есть `coordinator`;
- есть `participants`;
- сначала coordinator спрашивает всех "сможешь commitить?";
- потом, если все согласны, рассылает финальное решение `COMMIT`;
- если хотя бы один не готов, рассылается `ROLLBACK`.

Главная цель:

**сделать так, чтобы все участники либо commit'нули, либо все откатились.**

----------------------------------------------------------------------------------------------------

## Где это вообще нужно

2PC нужен, когда одно логическое действие затрагивает:

- несколько БД;
- БД + JMS/XA-очередь;
- несколько XA-совместимых ресурсов;
- несколько resource manager'ов под управлением одного transaction manager.

Пример:

```text
перевод денег:
  update DB-1
  update DB-2

хочется:
  либо обе записи committed
  либо ни одной
```

Внутри одной БД эта проблема решается обычной локальной транзакцией.
Между независимыми ресурсами нужен протокол координации.

----------------------------------------------------------------------------------------------------

## Компоненты 2PC

### Coordinator / Transaction Manager

Это координатор, который:

- открывает distributed transaction;
- собирает участников;
- инициирует `prepare`;
- принимает финальное решение;
- пишет его в свой лог;
- рассылает `commit` или `rollback`.

В Java-мире это обычно роль `JTA transaction manager`.

### Participants / Resource Managers

Это участники, которые:

- принимают локальные изменения;
- умеют отвечать на `prepare`;
- умеют зафиксировать `commit`;
- умеют сделать `rollback`;
- удерживают нужные блокировки до финального решения.

В XA-мире это обычно:

- XA-совместимая БД;
- XA-совместимый JMS provider;
- другой XA resource manager.

----------------------------------------------------------------------------------------------------

## XA

**XA** — это стандартный интерфейс взаимодействия между:

- transaction manager;
- resource manager.

Идея XA:

- coordinator не знает внутренних деталей конкретной БД;
- он работает через стандартный контракт;
- resource manager участвует в distributed transaction как XA participant.

В Java/Spring это обычно связано с:

- `JtaTransactionManager`
- `XADataSource`
- `XAConnectionFactory`

Важно:

- `XA + XA` -> настоящий 2PC возможен;
- `XA + non-XA` -> это уже компромисс, а не строгая глобальная атомарность;
- `non-XA + non-XA` -> настоящий 2PC не получится.

----------------------------------------------------------------------------------------------------

## Как работает 2PC

### Фаза 1. Prepare

Coordinator говорит всем участникам:

```text
prepare
```

Каждый participant:

- выполняет локальную подготовку;
- пишет нужную информацию в свой лог;
- проверяет, может ли гарантированно commit'нуть позже;
- удерживает блокировки и ресурсы;
- отвечает либо `PREPARED`, либо `ABORT`.

Смысл prepare:

- участник еще не commit'нул окончательно;
- но уже обещает, что если придет `COMMIT`, он сможет его завершить.

----------------------------------------------------------------------------------------------------

### Фаза 2. Commit / Rollback

Если **все** участники ответили `PREPARED`, coordinator:

- пишет в свой лог финальное решение `COMMIT`;
- рассылает всем:

```text
commit
```

Если хотя бы один участник сказал `ABORT`, coordinator:

- пишет `ROLLBACK`;
- рассылает всем:

```text
rollback
```

Схема happy path:

```text
Coordinator -> RM1: PREPARE
Coordinator -> RM2: PREPARE

RM1 -> Coordinator: PREPARED
RM2 -> Coordinator: PREPARED

Coordinator writes COMMIT decision

Coordinator -> RM1: COMMIT
Coordinator -> RM2: COMMIT
```

----------------------------------------------------------------------------------------------------

## Почему 2PC считается тяжелым

### 1. Это блокирующий протокол

После `PREPARE` участник:

- уже не может просто забыть о транзакции;
- удерживает состояние до финального решения;
- часто держит блокировки и ресурсы.

Если coordinator пропал в плохой момент, участник может зависнуть в prepared state и ждать.

### 2. Выше latency

Нужно:

- минимум две фазы взаимодействия;
- больше сетевых round-trip;
- больше дисковых записей в логи;
- больше coordination overhead.

### 3. Хуже availability

Если для commit нужен ответ и согласованность нескольких участников, то отказ любого из них влияет на весь flow.

### 4. Сильная связанность

Участники должны:

- поддерживать XA;
- доверять общему coordinator;
- жить в общей модели distributed transaction.

Для независимых микросервисов это часто плохой fit.

----------------------------------------------------------------------------------------------------

## Failure modes

### Сбой участника до `PREPARE`

Если participant упал до ответа:

- coordinator не получает `PREPARED`;
- финальное решение — `ROLLBACK`.

Это относительно простой случай.

### Сбой участника после `PREPARE`, но до `COMMIT`

Это уже неприятнее.

Участник:

- уже обещал commit;
- удерживает состояние;
- не знает финального решения, пока не восстановится и не узнает его у coordinator.

### Сбой coordinator после того, как все ответили `PREPARED`

Это самый известный неприятный сценарий.

Если coordinator успел собрать `PREPARED`, но не все узнали финальное решение:

- участники могут зависнуть в uncertain state;
- ресурсы удерживаются;
- доступность падает.

Именно поэтому 2PC называют blocking protocol.

----------------------------------------------------------------------------------------------------

## Почему 2PC плохо ложится на микросервисы

Микросервисная архитектура обычно строится вокруг идей:

- независимое владение данными;
- слабая связанность;
- асинхронность;
- отказоустойчивость через автономность сервисов.

2PC идет в обратную сторону:

- общий coordinator;
- общее commit-решение;
- общий failure domain;
- блокировки и ожидание;
- XA-поддержка у всех участников.

Поэтому в микросервисах 2PC часто считают:

- слишком тяжелым;
- слишком хрупким;
- слишком дорогим по latency и ops complexity.

Это не значит, что 2PC "плохой всегда".
Это значит, что для автономных сервисов он редко является дефолтным выбором.

----------------------------------------------------------------------------------------------------

## Где 2PC еще может быть оправдан

- небольшой controlled environment;
- ограниченное число участников;
- реальные требования к строгой атомарности;
- участники все внутри одной организации и под единым управлением;
- все ресурсы XA-capable;
- команда готова нести operational cost.

Примеры:

- enterprise-монолит или modular monolith с несколькими XA-ресурсами;
- старые enterprise integration сценарии;
- отдельные финансовые use case, где compromise unacceptable и среда строго контролируется.

----------------------------------------------------------------------------------------------------

## Где 2PC обычно плохой выбор

- длинный бизнес-процесс на минуты/часы;
- микросервисы с независимым владением данными;
- интеграция с внешними API;
- интеграция с системами без XA;
- Kafka/event-driven pipeline;
- сценарии, где важны availability и decoupling.

Если один из шагов:

- уже отправил email;
- дернул сторонний платежный gateway;
- вызвал внешний HTTP API;

то идея "сделаем один глобальный rollback" обычно уже неадекватна реальности.

----------------------------------------------------------------------------------------------------

## 2PC vs локальная транзакция

Это важно не путать.

Локальная транзакция:

- один resource manager;
- один commit point;
- rollback дешевый и естественный;
- высокая предсказуемость.

2PC:

- несколько resource manager'ов;
- coordinator;
- prepare + commit;
- больше логов, сетевых обменов и failure cases.

То есть 2PC — это не "чуть более сложный `@Transactional`".
Это другой класс задачи.

----------------------------------------------------------------------------------------------------

## 2PC vs Saga

2PC говорит:

```text
не commit'им никого, пока не убедимся, что commit'ить могут все
```

Saga говорит:

```text
каждый шаг делает свой локальный commit,
а при проблеме дальше выполняем компенсации
```

2PC:

- сильнее по атомарности;
- тяжелее по координации.

Saga:

- слабее по мгновенной консистентности;
- лучше по автономности и микросервисному fit.

----------------------------------------------------------------------------------------------------

## Что важно запомнить

- 2PC пытается дать глобальную атомарность между несколькими участниками.
- Для этого нужен coordinator и protocol `prepare -> commit/rollback`.
- XA — стандартный интерфейс для участия ресурсов в такой транзакции.
- 2PC блокирующий, дорогой по coordination и latency.
- Именно поэтому в микросервисах чаще выбирают Saga + Outbox, а не XA.
