# Distributed Transactions

**Распределенные транзакции** — это не "одна транзакция побольше", а проблема координации изменений
между несколькими независимыми ресурсами: разными БД, разными сервисами, БД + брокером сообщений.

Как только одно бизнес-действие требует записать данные не в один локальный resource manager,
сразу появляется вопрос:
как сделать так, чтобы система не уехала в противоречивое состояние,
если часть действий успела выполниться, а часть нет?

**Как правильно думать о проблеме?**

Пока все происходит внутри: одной БД; одного connection; одного transaction manager -- мы живем в
мире обычной локальной транзакции. Там все относительно просто: `BEGIN` + несколько SQL-операций +
`COMMIT` или `ROLLBACK`.

Но в распределенных транзакциях локальный `rollback` уже не спасает, потому что:
у каждого сервиса своя БД, чужой `COMMIT` уже мог произойти, внешняя система может быть недоступна,
сообщение может отправиться дважды, письмо уже могло уйти пользователю, часть шагов может быть
необратимой.

ACID

**межсервисная транзакция почти никогда не равна одной ACID-транзакции в духе одной БД.**

**в распределенных транзакциях нет ACID**

----------------------------------------------------------------------------------------------------

**На практике в микросервисах очень часто делают не что-то одно, а связку:**

- локальная транзакция в сервисе
- `Outbox` для надежной публикации событий
- `Kafka` или другой брокер как транспорт
- `Saga` для межсервисного процесса
- `Inbox` / dedup / идемпотентность на стороне consumer

**Это не дает магической глобальной ACID-транзакции. Зато дает более реалистичную и масштабируемую модель.**

## Главный конфликт

Хочется получить сразу все:

- строгую глобальную атомарность;
- простую реализацию;
- высокую доступность;
- слабую связанность сервисов;
- хорошую масштабируемость;
- минимальную latency.

На практике так не бывает.
Приходится выбирать tradeoff.
Отсюда и появляются разные подходы:

- `2PC / XA` — максимум атомарности, но высокая связанность и тяжелая координация;
- `Saga` — координация через локальные транзакции и компенсации;
- `Outbox` — надежная публикация событий без dual write;
- `Inbox / dedup / idempotency` — защита от дублей и повторной доставки;
- `eventual consistency` — сознательная модель, а не случайная ошибка.

## Что почти всегда нужно рядом

Как только речь идет о distributed transactions, рядом почти всегда появляются:
- `idempotency`
- `retry`
- `deduplication`
- `Inbox`
- `correlation id`
- `trace id`
- `saga id`
- `timeout handling`
- `observability`
- `audit trail`

**Почему:**
- сообщения могут прийти повторно
- шаг может завершиться, а ack потеряться
- consumer может упасть после обработки, но до commit
- compensation тоже может дать ошибку
- без трассировки очень трудно понять, где завис процесс

Подробнее: [Patterns & Failures](./patterns-and-failures.md)

## Проблемы и Чем их решают

- **Нет одного общего атомарного commit между сервисами** -> либо [2PC / XA](#2pc-xa), либо отказ от глобальной атомарности и переход к [Saga](#saga).
- **`dual write problem` (БД сохранили, событие не отправили или наоборот)** -> [Transactional Outbox](#transactional-outbox).
- **Дубликаты сообщений и повторная доставка** -> [Idempotency](#idempotency), [Inbox](#inbox), [processed_messages](#processed-messages), unique constraints.
- **Частично выполненный бизнес-процесс** -> [Saga](#saga), [compensating actions](#compensating-actions), явные статусы процесса.
- **Компенсация может быть неидеальной или необратимой** -> [compensating actions](#compensating-actions), проектирование компенсаций как отдельных бизнес-операций.
- **Временная рассинхронизация между сервисами** -> [Eventual consistency](#eventual-consistency), промежуточные статусы (`PENDING`, `FAILED`, `COMPENSATING`).
- **Зависшие процессы и шаги без ответа** -> [Timeout handling](#timeout-handling), [Retry policy](#retry-policy), monitoring, manual intervention flow.
- **Повторные ошибки при retry** -> делать retry только вместе с [Idempotency](#idempotency), [Retry policy](#retry-policy), backoff и лимитом попыток.
- **Потеря понимания, где именно сломался flow** -> [Observability](#observability), `correlation_id`, `trace_id`, `saga_id`, audit trail.
- **Сильная связанность и блокировки при глобальной координации** -> не тащить [2PC / XA](#2pc-xa) туда, где лучше работают [Saga](#saga) + [Transactional Outbox](#transactional-outbox).
- **Невозможно честно откатить внешний side effect** -> использовать refund/cancel/release как [compensating actions](#compensating-actions) и заранее признавать необратимые действия.
- **Проблемы порядка событий** -> [Partition key и порядок событий](#partition-key-ordering).

<a id="2pc-xa"></a>
## 2PC / XA

- есть coordinator
- есть несколько участников
- сначала все говорят "готов commitить"
- потом coordinator говорит всем либо `COMMIT`, либо `ROLLBACK`

**Плюсы:**
- строгая атомарность между участниками

**Минусы:**
- блокирующий протокол
- тяжелая координация
- выше latency
- хуже availability
- плохо ложится на независимые микросервисы и внешние системы

**Подробнее:** [2PC / XA](./2pc.md)

----------------------------------------------------------------------------------------------------

<a id="saga"></a>
## Saga

- нет одного общего глобального commit
- есть цепочка локальных транзакций в разных сервисах
- при ошибке выполняются компенсирующие действия

**Плюсы:**
- лучше подходит для микросервисов;
- хорошо сочетается с асинхронностью;
- нет тяжелого XA coordinator на весь процесс.

**Минусы:**
- логика сложнее;
- нет мгновенной глобальной консистентности;
- нужны компенсации, ретраи, таймауты, наблюдаемость.

**Подробнее:** [SAGA](./saga.md)

----------------------------------------------------------------------------------------------------

<a id="transactional-outbox"></a>
## Transactional Outbox

- не пытаться одновременно "сохранить в БД" и "отправить в брокер"
- в той же локальной транзакции, что и бизнес-данные, записать событие в `outbox` таблицу бд
- потом отдельный publisher или CDC публикует событие наружу

**Плюсы:**
- решает проблему `dual write`

**Минусы:**
- публикация обычно `at least once`
- дубликаты все равно возможны
- downstream должен быть идемпотентным

**Подробнее:** [Transactional Outbox](./outbox.md)

<a id="eventual-consistency"></a>
## Eventual consistency

Многие боятся eventual consistency как чего-то "неправильного".
На практике это просто честная модель:

- прямо сейчас разные части системы могут видеть разное промежуточное состояние;
- но через некоторое время и после завершения шагов / retry / compensation система приходит к
  согласованному бизнес-состоянию.

**Пример:**
```text
заказ уже есть
резерв товара еще не сделан
платеж еще не проведен
доставка еще не создана
```

Это не всегда ошибка.
Это может быть нормальная промежуточная стадия процесса.
Проблема начинается, если:
- нет таймаутов
- нет ретраев
- нет мониторинга
- нет понятной финальной модели состояния

<a id="idempotency"></a>
## Idempotency

**Idempotency** означает:

- повторный вызов не должен ломать бизнес-инвариант;
- одно и то же сообщение не должно повторно создавать тот же эффект;
- повторная доставка не должна приводить к двойному списанию, двойному резерву, двойному созданию записи.

Чем обычно достигается:

- стабильный `event_id`
- уникальные constraints
- upsert
- проверка "обрабатывали ли уже это событие"
- отдельная таблица `processed_messages`

Идея простая:

```text
если одно и то же событие пришло второй раз,
бизнес-результат должен остаться тем же
```

----------------------------------------------------------------------------------------------------

<a id="inbox"></a>
## Inbox

`Inbox` — это паттерн для входящих сообщений.

Идея:

- получить событие;
- проверить, не было ли оно уже обработано;
- если событие новое, выполнить локальную транзакцию;
- в той же транзакции отметить событие как обработанное.

То есть `Inbox` решает проблему:

```text
сообщение пришло повторно,
но бизнес-операцию второй раз выполнять нельзя
```

Обычно `Inbox` используется вместе с `Outbox`.

----------------------------------------------------------------------------------------------------

<a id="processed-messages"></a>
## processed_messages

`processed_messages` — это самая частая техническая реализация идемпотентности на стороне consumer.

Обычно там хранят:

- `message_id` или `event_id`
- `consumer_name`
- `processed_at`
- иногда `correlation_id` и статус обработки

Схема работы:

```text
1. получили сообщение
2. проверили processed_messages
3. если записи нет -> обрабатываем
4. в той же транзакции пишем, что сообщение обработано
5. если запись уже есть -> считаем это duplicate
```

Это один из самых практичных способов защиты от re-delivery.

<a id="compensating-actions"></a>
## Compensating Actions

Компенсирующее действие — это не rollback БД, а новое бизнес-действие, которое логически нейтрализует уже сделанный шаг.

Примеры:

- `charge` -> `refund`
- `reserve inventory` -> `release inventory`
- `create order` -> `cancel order`

Что важно:

- компенсация тоже может упасть;
- компенсация тоже должна быть идемпотентной;
- компенсация не всегда идеально симметрична исходной операции;
- некоторые действия вообще нельзя полноценно компенсировать.

Поэтому compensation — это часть бизнес-дизайна процесса, а не просто технический `rollback`.

<a id="retry-policy"></a>
## Retry Policy

Retry нужен, потому что многие ошибки временные:

- сеть недоступна
- брокер моргнул
- БД вернула transient error
- внешний сервис дал timeout

Но retry безопасен только если есть:

- idempotency
- ограничение по количеству попыток
- backoff
- понимание, какие ошибки retryable, а какие нет

Плохой retry:

- бесконечный
- без backoff
- на неидемпотентной операции

Хороший retry:

- ограниченный
- с backoff
- с observability
- с понятным финальным failure outcome

----------------------------------------------------------------------------------------------------

<a id="timeout-handling"></a>
## Timeout Handling

В распределенных процессах нельзя ждать "сколько угодно".

Нужно заранее решить:

- сколько ждать следующий шаг
- когда считать шаг потерянным
- когда делать retry
- когда запускать compensation
- когда эскалировать в ручной разбор

Иначе появляются:

- зависшие саги
- орфанные резервы
- навсегда `PENDING` объекты
- ручные разборы в проде

Timeout policy — это обязательная часть архитектуры distributed workflow.

<a id="observability"></a>
## Observability

Без наблюдаемости distributed transactions очень быстро становятся непрозрачными.

Минимум обычно нужен такой:

- `correlation_id`
- `trace_id`
- `saga_id`
- `event_id`
- audit trail по шагам
- статусы процесса и шагов

Нужно уметь ответить на вопросы:

- какая сага стартовала
- какой шаг завершился
- где произошла ошибка
- что уже компенсировалось
- что зависло и требует вмешательства

Observability здесь не nice-to-have, а часть корректности системы.

<a id="partition-key-ordering"></a>
## Partition Key И Порядок Событий

Если распределенный процесс идет через брокер вроде Kafka, нужно понимать, что порядок событий не возникает сам собой.

Обычно нужно:

- выбрать стабильный `partition key`
- например `orderId` или `paymentId`
- держать события одной сущности в одной partition

Что это дает:

- локальный порядок по одной сущности
- меньше хаоса в consumer logic

Что это не дает:

- глобальный порядок по всей системе
- автоматическое решение всех race condition

Поэтому порядок событий надо проектировать явно, а не надеяться, что брокер "как-нибудь сам".
