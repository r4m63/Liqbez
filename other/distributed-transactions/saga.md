# SAGA

## Что такое Saga

**Saga** — это способ выполнить длинную бизнес-операцию как последовательность локальных транзакций в разных сервисах или модулях.

Идея:

- каждый шаг делает **свой локальный commit**;
- если какой-то следующий шаг не удался;
- предыдущие шаги не откатываются общей ACID-транзакцией;
- вместо этого выполняются **компенсирующие действия**.

Коротко:

```text
Saga = local transactions + coordination + compensations
```

Главная цель:

**не глобальный rollback, а приведение системы к согласованному бизнес-состоянию.**

----------------------------------------------------------------------------------------------------

## Почему Saga вообще появилась

В микросервисах часто так:

- каждый сервис владеет своей БД;
- делать общий XA/2PC неудобно;
- часть шагов асинхронна;
- есть внешние API и необратимые побочные эффекты;
- важны автономность и доступность.

Поэтому вместо одной большой распределенной ACID-транзакции делают:

- много маленьких локальных транзакций;
- между ними — события или команды;
- при ошибке — компенсации.

Это и есть Saga pattern.

----------------------------------------------------------------------------------------------------

## Компенсация != rollback

Это самая важная мысль в теме Saga.

### Rollback

Rollback:

- работает внутри локальной транзакции;
- отменяет незакоммиченные изменения;
- не отменяет уже завершенный внешний эффект.

### Compensation

Компенсация:

- это новое бизнес-действие;
- оно логически нейтрализует прошлый шаг;
- но не делает вид, что прошлого шага "никогда не было".

Примеры:

- `charge payment` -> `refund payment`
- `reserve inventory` -> `release inventory`
- `create order` -> `cancel order`

Компенсация может быть:

- частичной;
- асинхронной;
- дорогой;
- неидеально симметричной.

----------------------------------------------------------------------------------------------------

## Из чего состоит Saga

У любой саги обычно есть:

- `saga id`
- набор шагов
- порядок переходов
- статусы шагов
- правила retry
- правила timeout
- компенсирующие действия
- correlation / tracing metadata

Нужно понимать:

- какой шаг идет следующим;
- что считается успехом;
- что делать при ошибке;
- когда запускать компенсацию;
- когда считать сагу окончательно проваленной.

----------------------------------------------------------------------------------------------------

## Базовый пример

Допустим, есть процесс оформления заказа.

Участвуют:

- `Order Service`
- `Inventory Service`
- `Payment Service`
- `Shipping Service`

### Happy path

```text
1. Order Service -> create order (PENDING)
2. Inventory Service -> reserve items
3. Payment Service -> charge
4. Shipping Service -> create shipment
5. Order Service -> mark order CONFIRMED
```

Каждый шаг:

- делает локальную транзакцию;
- коммитит ее;
- инициирует следующий шаг.

### Failure path

Если доставка не создалась:

```text
shipping failed
=> refund payment
=> release inventory
=> cancel order
```

То есть откат идет не через глобальный rollback, а через цепочку compensating actions.

## Два основных вида Saga

### 1. Choreography

Нет одного центрального координатора.

Сервисы:

- публикуют события;
- слушают события друг друга;
- сами понимают, что делать дальше.

Пример:

```text
Order Service publishes OrderCreated
Inventory Service listens and publishes InventoryReserved
Payment Service listens and publishes PaymentCharged
Shipping Service listens and publishes ShipmentCreated
```

Если что-то падает:

- сервис публикует failure event;
- другие сервисы запускают свои компенсации.

Плюсы choreography:

- хорошо ложится на event-driven architecture;
- сервисы более автономны;
- нет отдельного orchestration service;
- простой старт для небольших flow.

Минусы choreography:

- логика процесса размазана по многим сервисам;
- тяжело увидеть весь flow в одном месте;
- сложнее дебажить;
- выше риск `event spaghetti`.

----------------------------------------------------------------------------------------------------

### 2. Orchestration

Есть центральный оркестратор.

Он:

- знает модель процесса;
- запускает шаги;
- ждет ответы;
- принимает решения о retry и compensation;
- держит состояние саги.

Пример:

```text
Client -> Saga Orchestrator

orchestrator -> Order Service: createOrder
orchestrator -> Inventory Service: reserve
orchestrator -> Payment Service: charge
orchestrator -> Shipping Service: createShipment
```

Если shipping упал:

```text
orchestrator -> Payment Service: refund
orchestrator -> Inventory Service: release
orchestrator -> Order Service: cancel
```

Плюсы orchestration:

- весь flow виден в одном месте;
- проще дебажить;
- проще менять сценарий;
- легче делать timeout / retry policy;
- лучше подходит для длинных процессов.

Минусы orchestration:

- появляется центральный компонент;
- он может стать слишком сложным;
- при плохом дизайне получается `god service`.

----------------------------------------------------------------------------------------------------

## Когда choreography подходит лучше

- процесс короткий;
- шагов немного;
- система и так event-driven;
- команды сервисов умеют работать с асинхронными событиями;
- нет необходимости держать сложную central state machine.

## Когда orchestration подходит лучше

- процесс длинный;
- шагов много;
- важны прозрачность и трассировка;
- нужны сложные timeout / retry rules;
- бизнес-flow часто меняется.

----------------------------------------------------------------------------------------------------

## Изоляция и промежуточные состояния

У саги нет такой же изоляции, как у одной БД-транзакции.

Это значит:

- промежуточные состояния могут быть видны другим сервисам;
- другие процессы могут читать данные между шагами;
- бизнес должен уметь жить с состояниями вроде `PENDING`, `RESERVED`, `COMPENSATING`, `FAILED`.

Пример:

```text
заказ уже создан,
но платеж еще не проведен
```

Это нормальное промежуточное состояние для Saga.

Поэтому в дизайне саги важно:

- явно задавать статусы;
- понимать allowed transitions;
- не притворяться, что процесс "атомарный как SQL transaction".

----------------------------------------------------------------------------------------------------

## Что хранить в состоянии Saga

Обычно полезно хранить:

- `saga_id`
- `correlation_id`
- `current_step`
- `status`
- `payload/context`
- `started_at`
- `updated_at`
- `retry_count`
- `last_error`

Если orchestration-based подход:

- состояние обычно хранится у оркестратора.

Если choreography-based:

- общее состояние может быть размазано;
- поэтому correlation/tracing особенно критичны.

----------------------------------------------------------------------------------------------------

## Таймауты и зависшие саги

Нельзя проектировать Saga так, будто все ответы придут мгновенно и всегда.

Нужно явно решать:

- сколько ждать следующий шаг;
- сколько делать retry;
- когда запускать compensation;
- когда помечать сагу как `FAILED`;
- кто поднимает алерт на stuck saga.

Без этого легко получить:

- зависшие процессы;
- орфанные резервы;
- списанные деньги без финального результата;
- ручные разборы в проде.

----------------------------------------------------------------------------------------------------

## Какие компенсации сложны или неполны

Не все операции компенсируются идеально.

Примеры:

- письмо уже ушло пользователю;
- внешний банк провел списание, а refund — это уже новая операция;
- партнерская система приняла запрос, но отмена занимает часы;
- физическая отгрузка уже ушла со склада.

Отсюда вывод:

- компенсация должна проектироваться как бизнес-процесс;
- нельзя считать ее технической мелочью;
- иногда компенсация означает не "отменить", а "смягчить последствия".

----------------------------------------------------------------------------------------------------

## Что почти всегда нужно рядом с Saga

- `Outbox`
- `idempotent handlers`
- `Inbox / processed_messages`
- `retry`
- `timeout policy`
- `dead letter handling`
- `correlation id`
- `observability`

Почему:

- шаг может быть вызван повторно;
- событие может прийти повторно;
- compensation тоже может ретраиться;
- без трассировки сложно понять, какой шаг реально завершился.

----------------------------------------------------------------------------------------------------

## Типичные ошибки

- Нет идемпотентности у шагов и компенсаций.
- Нет явных статусов процесса.
- Нет timeout handling.
- Нет понимания, что делать со stuck saga.
- Choreography используется там, где процесс уже слишком сложный.
- Компенсация проектируется "потом разберемся".
- Сервис публикует событие ненадежно без Outbox.
- Команда обещает пользователю мгновенную глобальную консистентность там, где ее нет.

----------------------------------------------------------------------------------------------------

## Saga vs 2PC

2PC говорит:

```text
все commit'им атомарно или не commit'им никого
```

Saga говорит:

```text
каждый сервис делает локальный commit,
а если что-то пошло не так дальше,
идем по compensating actions
```

2PC сильнее по атомарности.
Saga лучше по автономности и микросервисному fit.

----------------------------------------------------------------------------------------------------

## Что важно запомнить

- Saga — это координация длинного процесса через локальные транзакции.
- Компенсация — это новое действие, а не rollback прошлой БД-транзакции.
- Choreography проще стартует, orchestration проще понимать и сопровождать в сложных flow.
- У саги нет глобальной ACID-изоляции, поэтому промежуточные состояния надо проектировать явно.
- Без idempotency, timeout policy и observability Saga быстро превращается в production pain.
