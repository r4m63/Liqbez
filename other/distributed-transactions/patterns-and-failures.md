# Patterns & Failures

## Почему здесь так много вспомогательных паттернов

Как только система уходит от одной локальной транзакции к:

- нескольким сервисам;
- сообщениям;
- ретраям;
- внешним API;

сразу появляются новые классы ошибок:

- дубликаты;
- переотправка;
- потерянный ack;
- зависший процесс;
- частично выполненная компенсация;
- рассинхрон между БД и брокером;
- промежуточные бизнес-состояния.

Поэтому рядом с distributed transactions почти всегда стоят вспомогательные паттерны.

----------------------------------------------------------------------------------------------------

## Idempotency

**Idempotency** означает:

- повторный вызов не должен ломать бизнес-инвариант;
- одно и то же сообщение не должно повторно создавать тот же бизнес-эффект.

Примеры:

- второй `OrderCreated` не должен создать второй заказ;
- второй `PaymentCaptured` не должен списать деньги еще раз;
- повторное `ReserveInventory` не должно удвоить резерв.

Практические способы:

- уникальный `event_id`
- `processed_messages`
- `inbox` table
- уникальные constraints
- upsert
- business key based deduplication

Главная мысль:

**если в системе есть ретраи и сообщения, идемпотентность почти всегда обязательна.**

----------------------------------------------------------------------------------------------------

## Inbox Pattern

`Inbox` — это паттерн для входящих сообщений.

Идея:

- before processing проверить, не обрабатывали ли уже это сообщение;
- если не обрабатывали, выполнить локальную транзакцию;
- в той же транзакции отметить сообщение как обработанное.

Схема:

```text
receive message
check inbox/processed_messages
if new:
  do local business transaction
  mark message processed
else:
  skip duplicate
```

Это типичный компаньон к Outbox.

## Retry

Retry нужен, потому что многие ошибки временные:

- сеть моргнула;
- брокер недоступен;
- БД дала transient error;
- внешний сервис вернул timeout.

Но retry опасен, если:

- операция неидемпотентна;
- нет лимита попыток;
- нет backoff;
- нет distinction между transient и permanent error.

Хороший retry policy обычно включает:

- ограничение по количеству попыток;
- backoff;
- jitter;
- классификацию ошибок;
- понятный финальный failure outcome.

----------------------------------------------------------------------------------------------------

## Timeout handling

Если нет явного timeout policy, любая distributed workflow рано или поздно начнет зависать.

Нужно заранее определить:

- сколько ждать ответ шага;
- когда считать шаг потерянным;
- когда переходить к compensation;
- когда эскалировать в manual review;
- кто отвечает за stuck processes.

Без этого появляются:

- орфанные резервы;
- саги в вечном `IN_PROGRESS`;
- ручные ночные разборы.

----------------------------------------------------------------------------------------------------

## Compensation failure

Очень важный и часто забытый сценарий:

- основной шаг упал;
- запускаем compensation;
- компенсация тоже падает.

Это означает:

- нужны retry policy и для compensation тоже;
- compensation должна быть идемпотентной;
- нужна observability именно для compensation chain;
- иногда нужен ручной intervention flow.

Нельзя проектировать систему так, будто compensation "всегда проходит с первого раза".

----------------------------------------------------------------------------------------------------

## Eventual consistency window

Между шагами распределенного процесса почти всегда есть окно, где состояние временно не синхронно.

Пример:

```text
order status = PENDING
inventory already reserved
payment not charged yet
```

Это normal operating mode для многих Saga-based систем.

Важно:

- явно моделировать такие состояния;
- не обещать пользователю мгновенную глобальную консистентность;
- понимать, какие read model и UI корректны в этом окне.

----------------------------------------------------------------------------------------------------

## Наблюдаемость

Distributed workflow без observability быстро становится неуправляемым.

Минимум обычно нужен такой:

- `correlation_id`
- `trace_id`
- `event_id`
- `saga_id`
- audit trail по шагам
- понятные финальные и промежуточные статусы

Нужно уметь ответить на вопросы:

- какая сага стартовала;
- какой шаг завершился;
- какой шаг ретраится;
- где именно она зависла;
- какая компенсация уже прошла, а какая нет.

## Типовые failure scenarios

### 1. Событие не опубликовано

Причина:

- dual write без Outbox;
- приложение упало после локального commit.

Последствие:

- downstream вообще не узнает о событии.

### 2. Событие опубликовано дважды

Причина:

- retry producer'а;
- relay упал после publish, но до mark-as-published;
- consumer replay.

Последствие:

- без idempotency можно сделать двойной side effect.

### 3. Consumer обработал, но не зафиксировал свой прогресс

Причина:

- обработка уже прошла;
- offset / inbox mark / ack не были зафиксированы.

Последствие:

- после рестарта сообщение приходит снова.

### 4. Compensation не сработала

Причина:

- timeout;
- внешний сервис недоступен;
- неидемпотентная компенсация;
- ошибка в business logic.

Последствие:

- процесс застревает в partially compensated state.

### 5. Stuck saga

Причина:

- не пришел ответ;
- event lost;
- consumer умер;
- timeout policy не спроектирована.

Последствие:

- бизнес-объект навсегда остается в промежуточном состоянии.

## Decision matrix

| Ситуация | Обычно лучше |
| --- | --- |
| Нужна строгая атомарность между небольшим числом XA-ресурсов | `2PC / XA` |
| Длинный межсервисный бизнес-процесс | `Saga` |
| Надо надежно опубликовать событие после локального commit | `Outbox` |
| Есть риск повторной доставки и дублей | `Inbox + idempotency` |
| Есть Kafka/event-driven integration | `Outbox + idempotent consumers + tracing` |

----------------------------------------------------------------------------------------------------

## Частые анти-паттерны

- Надеяться на "магический exactly-once" на уровне всей системы.
- Использовать `@Transactional` как будто он распространяется на соседние сервисы.
- Делать retry на неидемпотентный side effect.
- Не хранить event id и correlation metadata.
- Делать Saga без таймаутов и без stuck-process handling.
- Строить choreography на длинном процессе с десятком сервисов и потом терять контроль над flow.
- Путать техническую доставку сообщения с бизнес-успехом шага.

----------------------------------------------------------------------------------------------------

## Что почти всегда стоит сделать

- Ввести явные business states.
- Ввести стабильные `event_id`.
- Сделать handlers идемпотентными.
- Спроектировать retry policy отдельно для main path и compensation path.
- Сделать alerты на stuck saga / lag / repeated failures.
- Логировать `correlation_id`, `trace_id`, `saga_id`.
- Сразу договориться, какие действия реально компенсируемы, а какие нет.

----------------------------------------------------------------------------------------------------

## Что важно запомнить

- В distributed systems failure handling — это часть happy path, а не edge case.
- Outbox без idempotent consumer не дает полной надежности.
- Saga без observability очень быстро становится неуправляемой.
- Retry полезен только вместе с idempotency, backoff и timeout policy.
- Самая частая практическая модель: local transaction + Outbox + idempotent consume + compensation where needed.
