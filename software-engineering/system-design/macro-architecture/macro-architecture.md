# Macro-Architecture. Архитектура приложения

Как система разбита на deployable units: приложения, сервисы, процессы, базы данных, очереди,
хранилища и внешние интеграции; как эти части взаимодействуют между собой, где развёрнуты и
кто за что отвечает.

- Modular Monolith
- Microservices
- SCS
- SOA
- BFF
- EDA
- Serverless
- Distributed Monolith — как анти-паттерн
- CQRS / Event Sourcing — как macro-level pattern, если влияет на всю систему


## Modular Monolith

Архитектурный стиль, при котором система разворачивается как одно приложение (процесс), но
внутри разделена на независимые модули с чёткими границами и контролируемыми зависимостями.
Вся основная бизнес-логика приложения находится в одном deployable unit.

Один process, один deployment, один runtime, обычно одна база данных.

Разница Модульного Монолита и просто Монолита: в монолите модули условные могут быть, а могут и не
быть; в модульном монолите модули - это архитектурные границы.
Модуль - самостоятельная часть системы отвечающая за свой контекст.

## Microservices

Архитектурный стиль, при котором система разделяется на независимые сервисы, каждый из которых
отвечает за свою бизнес область, разворачивается отдельно и взаимодействует с другими сервисами
через сеть.

Каждый сервис: отдельный process; отдельный deployment; отдельный runtime; часто отдельная база данных;
отдельный CI/CD pipeline; отдельное масштабирование.

Ставят входной микросервис api-gateway service. Сервисы общаются через: HTTP/REST; gRPC; Kafka;
RabbitMQ; events/messages. То есть коммуникация микросвервисов = вызов по сети, либо синхронная
(HTTP/gRPC), асинхронная (brokets/events)
